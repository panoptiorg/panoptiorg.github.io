Read a finding carefully
  • A finding is a route, not an exploit. sqli means untrusted data reaches a call that runs SQL. Passed as a parameter of a prepared query, that is harmless, and it is still reported. panopticode never runs your code.
  • The catalog bounds recall. What it does not name is not looked for. Every run also prints the calls it could not see into; read that list on every new codebase.
  • Scope matters. Code the frontend did not read has no map. A sink behind it is invisible.
  • gRPC and GraphQL only, for now. Plain HTTP between services, queues, caches and database round trips are not followed.

Beyond findings panopticode impact re-extracts one repository at a merge request's head, reuses the cached summaries of everything the change did not touch, and reports the routes it did. Summaries are cached by what the callees do, not by their code, so an edit that keeps a function's behaviour invalidates nothing above it. With --pg, the call graph and the contract summaries go to Postgres, and panopticode query answers questions over them: which services can reach these changed files, and by which calls.
